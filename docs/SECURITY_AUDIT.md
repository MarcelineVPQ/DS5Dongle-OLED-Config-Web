# Security Audit

**Audit date:** 2026-10-13 (helper programs, the XInput fix's files and the firmware-write hold added; first audit 2026-10-10, desktop app introduction)
**Scope:** the Electron main process, preload, renderer, device access, external links, build and dependency supply chain
**Overall posture:** **GOOD** for the threat model below; one platform gap is recorded and tracked (Linux OS sandbox).

## Threat model

The app runs locally and talks to one USB device. It loads no remote content and has no accounts or secrets. Outbound requests come only from the main process (the renderer has no network access): the signed update feed and its downloads on GitHub, and Sony's controller firmware version list (below). What matters:

1. **Renderer compromise** (e.g. a malicious dependency in the UI bundle) must not reach the OS or other USB devices.
2. **Navigation / window.open** must not load remote content into a privileged window.
3. **Self-update** (Phase 3) must not run a corrupted or unexpected binary.
4. **Supply chain**: dependencies are pinned, audited, and updated deliberately.

Windows and macOS keep `shell.openExternal` / `shell.openPath`; whether a launcher is installed is asked of `xdg-mime` asynchronously (3 s timeout, same environment), never blocking the main process; the page never supplies a URL or a path; **art colors** (`desktop:game-art-color`, a scan key only) are computed in the main process from the scanned art file with `nativeImage` (`artColor.ts`) and returned as `#rrggbb`, so the page never reads image pixels |
| Game setup changes (Linux) | `electron/main/games/{games,backup,processes,service}.ts`, `electron/main/ipc.ts` (`ApplyRequestSchema`, `UndoRequestSchema`) | the page sends only fix ids (`FixIdsSchema`: shapes the scanner builds, no paths or values, at most 500), a backup id (`BACKUP_ID`) and a `restart` list (`steam`/`heroic`/`lutris`, at most 3; strict objects); every change is resolved against a fresh scan, backed up first and undoable; a running launcher that owns a change is closed **only** when the page named it in `restart` (the review says "will be closed to save this change, then reopened" first), otherwise nothing is written and the page asks again; nothing is closed while a Proton/Wine game runs; closing never force-kills: Steam gets `steam -shutdown` (Flatpak: `flatpak run com.valvesoftware.Steam -shutdown`) by `execFile` (fixed argv, no shell, 15 s), Heroic and Lutris get SIGTERM on their main process, then the app waits up to 30 s (a timeout writes nothing and reopens any launcher it already closed); the launcher is started again through `startForUser` (`schemeHandler.ts`: `spawn(cmd, args, { detached, stdio: "ignore" })`, no shell), where the program is a fixed name (`steam`, `heroic`, `lutris`, or `flatpak run <app id>`) or the launcher's own absolute path from its running process (`/proc/<pid>/cmdline`, or Heroic's `APPIMAGE` from `/proc/<pid>/environ`), accepted only when its file name is the launcher's, it exists and it isn't under `/tmp`; the only argument ever copied is Steam's `-silent`; both run with `launcherEnv` (the user's real home, app-only variables dropped), so a dev copy's test HOME never reaches a launcher (security-tested) |

| Official controller firmware check | `electron/main/officialFirmware.ts`, `src/protocol/officialFirmware.ts` | **check only:** the app never downloads or installs Sony firmware. One outbound host, `fwupdater.dl.playstation.net` (`OFFICIAL_FIRMWARE_HOSTS`), one fixed URL (`/fwupdater/info.json`, the version list Sony's PlayStation Accessories app reads): a plain HTTPS GET with no body, no added headers, `credentials: "omit"`, `redirect: "error"`, a 10 s timeout and a 16 KiB cap (content-length and the bytes read); nothing about the user, the controller or the dongle is sent. | O1  | LOW      | **Linux sandbox on Ubuntu 23.10+ needs our AppArmor profile.** Where AppArmor restricts unprivileged user namespaces, electron-builder's AppImage `AppRun` (its probe is `unshare -Ur true`) starts the app with `--no-sandbox`. The one-time Linux setup (*Set up USB access*, pkexec) now also installs `resources/linux/ds5-dongle-configurator.apparmor` to `/etc/apparmor.d/` on such systems: an unconfined profile with `userns`, the same as Ubuntu's own for Chrome, Brave and VS Code, attached to the AppImage's `/tmp/.mount_*/{AppRun,ds5-dongle-configurator}` so the probe and the app both get it. Verified on Ubuntu 26.04: no `--no-sandbox`, the renderer in its own user and PID namespaces with seccomp (mode 2) and NoNewPrivs. Until the user runs the setup (or if they skip it) the app runs as before, without the OS sandbox.
