# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project Overview

Configurator for the **DS5 Dongle OLED Edition** firmware (`MarcelineVPQ/DS5Dongle-OLED-Edition`, a Pico 2 W DualSense Bluetooth bridge): an Electron desktop app (React + TypeScript), `electron-vite build`. `src/main.tsx` renders `src/desktop/DesktopApp.tsx` (the preload exposes `window.desktop`). The browser web tool was retired after 0.8.0 and removed; GitHub Pages serves the static download page in `site/`. One screen built around the live controller (screenshots in `docs/screenshots/`).

The firmware repo is `~/projects/DS5Dongle`; its `CLAUDE.md` documents the device protocol (`src/cmd.cpp`, `src/vendor_itf.{h,cpp}`).

## Architecture

- **Transport** (`src/protocol/transport.ts`, `webUsbTransport.ts`): WebUSB vendor control transfers to the firmware's configurator interface (class 0xFF). GET `0xC1/0x01`, SET `0x41/0x02`, wValue = report id, payload ≤ 63 bytes **without** a report-id byte. ADR-0001.
- **Client** (`src/protocol/bridgeClient.ts`): `identity()` (`0xF1`, `DS5O`, protocol major must equal `SUPPORTED_PROTO_MAJOR`), `command(func, args)` sends `0xF6` and polls `0xF1` until the sequence matches and the result leaves `pending`; reboot/BOOTSEL resolve `"gone"`. Codecs: `config.ts` (37-byte `Config_body`), `remap.ts`.
- **Hook** (`src/hooks/useDs5Bridge.ts`): auto-connects to an already-permitted device, reconnects on USB connect/disconnect, tracks `config` (on the dongle's RAM), `savedConfig` (in flash as far as we know) and `draft`.
- **Desktop shell** (`src/desktop/`): `DesktopApp.tsx` has a navigation rail on the right edge (`AppRail.tsx`: Controller, Dongle, Games on Linux, App settings, About, dongle status, pin with Ctrl+B), debounces draft changes into `applyConfig` (live), and the one save bar (`SaveBar.tsx`: Revert / Save to the board for every board setting, or Save to profile; see "Page rules" 4). With no dongle connected it shows `SetupScreen.tsx` (first-time setup of a Pico in BOOTSEL with the firmware bundled in the app).
- **Live controller** (`src/desktop/live/`): `ControllerView` = `LiveController` (AL2009man's art, `src/assets/dualsense.svg`, generated by `tools/prepare_controller_art.py`; live state painted onto `data-part` elements, polled from firmware `0xF0` by `useLiveInput`) as the main view of a `SplitView` (`accordion/Section.tsx`), with the Controller page's sections (`PartPanel.tsx`, bodies from `pages/`), the Pico 2 W page (`dongle/DonglePage.tsx`) or App settings' sections beside it; a click on a part opens its section. **The accordion holds settings and actions only**: readouts and info (Pico diagnostics, Controller info, Games → Home's This computer, a game's details) go in the page's main view as `MainBlock`s (`accordion/MainBlock.tsx`: always shown, no fold; the Pico page reads the board once a second while it's shown, `useDongleTelemetry` in `dongle/DongleDashboard.tsx` over `usePoll` in `usePoll.ts`, which pauses while the window is hidden), and `tools/list_settings.mjs` fails a Section with no control or action. Nothing folds inside a section body, a main-view block or a gate screen (no `<details>`: passed checks, legends, Sony's update steps, HDR's Set it up yourself, the Windows USB repair's script are shown, compact; a long explanation goes behind the ⓘ; gated by `tests/unit/noFolds.test.ts`: no `<details>` / `<summary>` anywhere in `src/`). Every popup menu is the one `MenuButton` (`src/desktop/MenuButton.tsx`: the panel's ⋮, Games' Show; top layer, ↓ / Enter opens on the first item, arrows / Home / End, Escape back to the button); what the user ticks or types (a game's Feedback) is a setting, so a Section. A hidden panel stays hidden: a deep link from a notice, a tile or the drawing shows it, but arriving through the rail's task dot (`revealSection(…, { keepHidden: true })`) only opens and marks the section (the dot shows on the page's rail item, `panelTasks`; scrolled to and flashed when shown). The rail item of the page you're on is the one way to show or hide the panel (`togglePanel`), on every page alike: no show button on the page and no hide button in the panel's header (owner, dev.15); narrow, Escape also closes the drawer. **Gate screens** (`SetupScreen.tsx` with no board, Games' consent before anything is read) are one card without a panel: they come before the page exists. Narrow (900×650), the panel is a drawer with the same remembered state and ⋮ menu. A Row's visible hint (`sub`) and `dk-hint` paragraphs say only what you must know before acting (≤ 60 characters, or `// hint: MUST-SHOW — reason`); longer explanations go behind the ⓘ (`InfoTip`, Row's and SectionGroup's `info`), gated by `tools/list_hints.mjs`. The connected controller's model and colorway come from identity 1.2 (`colorways.ts`). Compact controls (incl. `BusyButton`, AVNetworkMonitor's busy-button behavior) in `controls.tsx`, styles in `desktop.css`.
- **Electron main** (`electron/main/index.ts`): single instance; session grants only WebUSB to the app origin and only the devices in `devices.ts`; all other permissions denied; navigation and window.open blocked (allowlisted https links open externally, `urls.ts`). Preload (`electron/preload/index.ts`) exposes only `window.desktop`.

## Load-bearing rules

- **Desktop UI must be compact and fill the window** (user requirement): ~13px type, tight padding, a 100vh grid shell, only the page body scrolls. No zoom hacks. Match the OLED's zero-based naming (FAV0–FAV3, slots 0–3).
- **One theme system, many themes** (user requirement): every color comes from the theme tokens (`--bg-*`, `--text-*`, `--border-*`, `--dk-accent`, `--status-good|warn|bad`), which the themes (Light, Dark, Desktop, Controller, game pages via `scopedAccent`) and Color vision set in one place (`desktop.css` tokens, `theme/desktopPalette.ts`, `live/controllerAccent.ts`, `colorVision.ts`). New UI never hard-codes a color or styles a native control on its own (`accent-color` is set once on `.dk`). Exceptions are physical things drawn as they really look (the controller's LEDs, the OLED console, game art overlays) and the 42PS brand colors in Credits.
- **Light theme uses its own deeper greens and greys** (`--dk-*` tokens in `desktop.css`); the web tool's pale accent is unreadable on the desktop.
- **Never use AI-drawn or traced controller art.** Use the purchased Zacksly pack (CC BY 3.0, `assets/PS5 Button Icons and Controls/`, credit required) or the MIT AL2009man Gamepad-Asset-Pack.
- **Security baseline** is gated by `.hooks/check_electron_security.sh`, `.hooks/check_dom_sinks.sh` and `tests/security/`. Changing window/session/CSP/allowlists requires updating `docs/SECURITY_AUDIT.md` and those tests.
- **Automatic update checks off = no network at startup** (owner decision, 2026-10-15): with *Check for updates automatically* off the app fetches nothing on its own, the update feed (app, firmware, Proton in a Games scan, the dev preview) and Sony's firmware list included. It goes online only when the user presses a check button (Check for updates in App settings and on the Pico 2 W page's Firmware, the setup screen's Check for updates, the Development channel dialog's check, Refresh on Controller info) or Install. Main enforces it (`firmwareFeed` / `protonFeed` / `devChannelPreview`, the "asked" flag on the IPC); new network code takes the same gate and joins `tests/integration/updateConsent.test.ts` / `tests/unit/gamesFeedConsent.test.ts`. With it on, one check is one fetch of the feed (`FeedCache`).
- **Protocol changes** land in the firmware first, then the client, the simulated dongle (`src/protocol/simulatedDongle.ts`, also the tests' fake) and the tests in the same change.
- **Dependencies**: exact versions, chosen ≥ 2 weeks after release. Gated: `tests/unit/dependencies.test.ts` rejects `^`/`~`/ranges, `.npmrc` has `save-exact=true`, Dependabot waits 14 days (`cooldown`).
- **Gates, not prose** (`npm run gates` + tests, all in CI): the theme gate (`.hooks/check_theme_colors.mjs`) walks `.css`, `.tsx` and `.ts`; only its `TOKEN_SOURCES` files (the palettes) are exempt by path, anything else marks the line `theme-exempt: <reason>`. Long visible hints need a must-show reason (`tools/list_hints.mjs --check`). Every inline `eslint-disable` is listed in `docs/LINT_SUPPRESSIONS.md` (`tests/unit/lintSuppressions.test.ts`; an unused disable is an ESLint error). Every duplicate candidate has a verdict in `docs/DEDUPE_AUDIT.md` (`tools/list_duplicates.mjs --check`). No byte-identical files (`tools/check_identical_files.mjs`; with the firmware repo's path as an argument it checks across both). Every loop that waits or sits on a hot path has a `// loop: VERDICT — reason` comment (`tools/list_loops.mjs --check`, see "Loop pass"). Every cache and memo kept in a module, class, closure or ref has a `// cache: VERDICT — key=…; invalidated=…; bound=…` comment (`tools/list_caches.mjs --check`, see "Cache pass"). Every acquisition (listener, timer, subscription, stream, device, process, observer, effect) names its release point in a `// lifetime: VERDICT — …` comment (`tools/list_lifetimes.mjs --check`), and the leak test passes (see "Lifetime pass"). Every About → Coming soon entry maps to a BACKLOG row with a matching status, and every user-facing row still to do has an entry (rows ending "(internal)" are exempt; `tests/unit/roadmapBacklog.test.ts`). An allowlist entry names the finding/batch that removes it.
- **Linux dev quirks** (ADR-0004): `--no-sandbox` (AppArmor userns restriction), GPU rendering on by default (App settings → Hardware acceleration; a GPU crash turns it off for the next start), zoom pinned to 100%. When restarting the app from a shell, kill by the anchored full path (`pgrep -f "^$PWD/node_modules/electron/dist/electron"`; unanchored patterns also match your own shell and kill it): it is single-instance, so a stale hidden copy blocks every new launch.

## Page rules

The cross-page rules from the information-architecture audit (2026-10-16, owner approved all of its Q1–Q10). One place: here. Every page follows them; the two written exceptions are marked. Mechanical checks are named after each rule.

1. **A hardware zone is its name and a spec line in the title, then its live data** (the Pico 2 W page's OLED and board zones; the Controller page: model, colorway and status line, then the tiles).
2. **One fact, one place per page.** A value shown in a tile isn't repeated in a card or a section on the same page; across pages the same reading uses the same words and units (signal is "Excellent · −5 dB"). A game page's glance tiles use the panel's section names and order, and a tile never says what its section's status says (`tests/integration/gamePage.test.ts`, "a tile never repeats its section's status").
3. **The panel header: the title names what the settings apply to; the sub-line says where they're kept and how they save**, one `desktop.panelSub.<page>` string per page, no version, no status (`tests/unit/pageRules.test.ts`). **Exception (Q8): About's panel is a table of contents** (its sections list the texts' chapters; the text is the main view), and its sub-line says what the texts are.
4. **One save model (Q1): every board setting is saved by the one save bar** (`SaveBar.tsx`), on the pages whose settings it saves (the Controller and Pico 2 W pages) and nowhere else: App settings (this PC, saved as you change them), Games and About have no bar. The config applies live and the bar saves it to flash; buttons, stick curves, calibration and the PC sleep options are staged drafts (`live/boardDrafts.tsx`) the bar writes with Save and drops with Revert. No section has its own Save / Apply / Revert; a game's profile is saved by the bar's Save to profile. Gates: `tests/unit/oneSaveBar.test.ts` (no save/revert labels or direct board writes outside the bar and the drafts), `tests/integration/saveBar.test.ts`.
5. **Section anatomy: settings → its live meter → its test group, last, titled "<Sony term> test".** A standalone readout belongs in the main view (a `MainBlock`). **Exception (Q2): a live meter that shows the section's own settings working stays in the section, last before its test** (Adaptive triggers' Pull, Haptic feedback and Speaker level meters). Checked in `tests/integration/accordion.test.ts` ("every section with a test ends with it").
6. **A section has something to do in its current state.** When it has nothing (Q9), it shows its header and status only, no body (`Section`'s `idle`: no chevron, no pin, nothing to open); every section that opens has a control in it (`accordion.test.ts`' inventories; `tools/list_settings.mjs` for sections that never have one).
7. **A problem shown anywhere carries its fix or a link to it** (Set up USB access where games can't reach the controller, Install the DualSense Proton build from a game's Compatibility, an update's banner).
8. **Same action, same label, everywhere**: "Check for updates", "Set up USB access" (one action for the app's and the games' USB rule, Q4), "Edit on the Controller page".
9. **A control is shown only when it can act** (no greyed-out placeholder: say the state instead, e.g. "✓ Installed"); a switch that depends on the one above it may show disabled while that one is off. A tile is a button only if all its siblings are, or it is visibly marked.
10. **Panel sections in order of use, the danger zone (reset, forget, delete) last.** The Controller page keeps the drawing's top-to-bottom order; the Pico 2 W page starts with the OLED screen (Q10; Firmware keeps its yellow dot and the banner when an update waits).
11. **Main-view order follows the task**: the thing itself → its live state → its info → diagnostics and history (Games → Home: the Library before This computer).
12. **The same kind of block uses the same component**: spec lists (board specs, Controller info, a game's Details, This computer) one label/value list; readout tiles one tile; readouts a `MainBlock`, settings a `Section`.

The panel itself is shown and hidden only by the rail item of the page you're on (no show button on the page, no hide button in its header); narrow, Escape also closes the drawer.

## Loop pass

A standing rule for both repos (the AVIEW "serial-loop pass"). Never sample "hot paths" by eye: list every candidate mechanically and give each one a verdict.

1. **Every loop that waits or sits on a hot path carries a verdict comment**, added in the same commit as the loop. The gate enforces it: `node tools/list_loops.mjs --check` (in `npm run gates`, pre-commit and CI); the firmware's `tools/list_loops.py --check` runs in its CI.
   - App: `tools/list_loops.mjs` (TypeScript compiler API) lists every `for`/`while`/`do` loop and array iteration callback (`.map`, `.forEach`, `.reduce`, `.filter`, `.some`, `.every`, `.find*`, `.flatMap`, `.sort`) in `src/` and `electron/` that awaits, runs on a hot path (render, useEffect, rAF, setInterval, a poll, a WebUSB handler, the audio worklet, the game library scan, or anything those call), or is nested in another loop.
   - Firmware: `tools/list_loops.py` lists every loop in `src/` with where it runs (core1, core0's main loop, a callback, an ISR, boot), busy-waits and nesting.
2. **The comment goes on the loop's line or the line above:** `// loop: VERDICT — reason` (`{/* loop: … */}` inside JSX). If several loops share a line, one comment covers them all.
   - **PARALLELIZE**: independent async work per step. Run it with a bound.
   - **BATCH**: one call, report or write instead of N.
   - **SERIAL-REQUIRED**: give the reason. It is one of: the board's vendor HID interface is one session (requests must not interleave); protocol or transaction order; retry/backoff; a deadline; a data dependency.
   - **HOT-PATH-OK**: runs per frame or poll, but N is small and bounded. State N.
   - **FIX-HOT-PATH**: allocation, sort, regex or O(n²) work per frame or poll; work while the window is hidden (breaks the lean rule). In firmware: unbounded or blocking work on core1, flash access on core1, a busy-wait without a timeout.
   - **NOT-WORTH**: tiny N (state it), or startup-only / rare.
3. **"Parallel" means as parallel as the target allows, never unbounded.** The board is one HID session, so its requests stay serial.
4. **Re-run the full pass when a release touches hot paths** (render, polls, input, the library scan, core0's loop, core1). Run both listers, re-check every verdict, and update the tables in `docs/LOOP_PASS_<date>.md` (this repo holds the doc for both repos). Then fix PARALLELIZE, BATCH and FIX-HOT-PATH rows in batches, biggest effect first, with tests. The owner picks the batches.

## Lifetime pass

A standing rule for both repos (the AVIEW pass pattern, for resource lifetimes). Never review "who cleans this up" by eye: list every acquisition mechanically and give each one a verdict.

1. **Every acquisition names its release point, in the same commit that adds it**: `// lifetime: VERDICT — release point or reason`, on its line or in the comment block right above (`{/* lifetime: … */}` in JSX). The gate enforces it: `node tools/list_lifetimes.mjs --check` (in `npm run gates`, so `npm run check` and CI); the firmware's `tools/list_lifetimes.py --check` runs in its CI.
   - App: `tools/list_lifetimes.mjs` (TypeScript compiler API, sharing `tools/ts_program.mjs` with the loop and cache listers) lists every `addEventListener`, emitter `.on/.once`, `onX =` handler, the app's own `onX(listener)` subscriptions, `ipcMain.handle`, `setInterval` / `setTimeout` / `requestAnimationFrame`, `usePoll`, `getUserMedia` / `AudioContext` / worklets, observers, WebUSB/HID/PICOBOOT opens, spawns (and systemd-run units), file watchers, sockets, Electron windows/trays/menus, object URLs, and every `useEffect` / `useLayoutEffect` (with whether it returns a cleanup).
   - Firmware: `tools/list_lifetimes.py` lists every heap allocation (`malloc`, `new`, `queue_init`, `opus_*_create`), every `std::` container and every by-value copy of one, container growth, timers/alarms and handler registrations, with where it runs (core1, core0's loop, a callback, an ISR, boot).
2. **Verdicts:**
   - **OK**: name where it is released: an effect cleanup (unmount / deps change), `stop()` / `close()` / `off()`, the window closing, a device disconnect, "fires once".
   - **LEAK**: never released, or too late. State the impact.
   - **WASTE**: keeps running while the window is hidden or after it is no longer needed (the lean rule: UI-only work stops when `useWindowShown()` is false).
   - **HOT-ALLOC**: acquired or allocated per frame, render, report or main-loop pass.
   - **NOT-WORTH**: one per app or boot, lives until quit/reset by design, or rare and small. Say why.
3. **The leak test must pass** (`tests/integration/leaks.test.ts`, in `npm test`): every main page, accordion section and main-view block (Controller page, Pico 2 W page and App settings with every section and block opened, About, Sticks & calibration, Speaker, Microphone with the Mic Test running, Games Home, a game page) mounts and unmounts 50 times and the live listeners, timers/rAF, mic tracks, AudioContexts, observers and `window.desktop` subscriptions come back to baseline. A new page or panel joins its `PAGES` list in the same commit.
4. **Re-run the full pass when a release adds pages, polls, audio or device code.** Run both listers, re-check every verdict, and update the tables in `docs/LIFETIME_PASS_<date>.md` (this repo holds the doc for both repos). LEAK, WASTE and HOT-ALLOC rows are fixed in batches, biggest effect first, with tests. The owner picks the batches.

## Error pass

A standing rule for both repos, made after three actions failed silently in one day (Apply refused by the IPC check, a write refused while Heroic ran, the library disappearing on "Stop checking"). Full table: [`docs/ERROR_PASS_2026-10.md`](docs/ERROR_PASS_2026-10.md).

1. **No silent failure.** Every error a user's action can hit is either **shown**, in plain words (what happened, what to do), in all 7 languages, never "dongle", or **logged on purpose**, with a one-line reason why the user needn't see it. An empty catch, `() => undefined` or a bare `void promise` is neither.
2. **Use the one mechanism**:
   - `.catch(shown("desktop.errors.…"))` / `showError(key)` (`src/desktop/shownError.ts`): the app's one pinned notice. A page with its own status line uses that instead.
   - `.catch(logged("why"))` / `logged("why")(cause)` (`src/errorText.ts`, also in the main process).
   - `causeText(cause)` for any error text put on screen: it takes off Electron's IPC wrapper and says a refused request (`BAD_REQUEST`) and board results in plain words.
   - Main process: a refused request answers `BAD_REQUEST` through `parseRequest` (ipc.ts). A failure of something the user did outside the page (a tray toggle, a link) goes to the page with `showMainError(key)` (fixed `MAIN_ERROR_KEYS`).
   - Text the main process or the protocol code puts in front of the user is never English: `throw new KeyedError(key, params)` or return `keyedText(key, params)` (`src/errorText.ts`); the page says it in the user's language through `causeText` / `shownText`. The start-failure dialog (no page) uses `mainText` (`electron/main/mainText.ts`). The gate refuses `english:` outside the Developer card, and `tests/integration/errorPassE3.test.ts` checks every key sent exists in all 7 locales.
3. **Every candidate carries one verdict**, in the same commit as the code: SHOWN (cite the key), LOGGED-OK (the reason), SILENT-BUG / SWALLOWED / FLOATING (name the batch), NOT-WORTH (why it can't fail, or why the "failure" is a state the caller shows), PASSES-ON (the caller has the verdict). Write it as a comment on the line or the line above, `// error: VERDICT — reason` (`{/* error: … */}` in JSX; for a catch, the `catch` line or its first line). `shown("key")` / `logged("why")` handlers and rethrows need no comment.
   - App: `tools/list_errors.mjs` lists every try/catch, `.catch`, `.then(ok, onRejected)`, `void` promise, floating promise, IPC handler and renderer IPC call, zod parse, child process, fetch, `JSON.parse` and failure field in a result type.
   - Firmware: `tools/list_errors.py` lists every failure path: dropped and checked status returns, failure returns, 0xF1 result codes, stored-data checks, drop counters, silent guards in user actions.
4. **Gates.** App: `node tools/list_errors.mjs --check` (in `npm run gates`, pre-commit and CI) and ESLint's `@typescript-eslint/no-floating-promises` (`ignoreVoid: false`: `void` only in front of a handled chain), `no-misused-promises` and `no-empty` (`allowEmptyCatch: false`). Firmware: `python3 tools/list_errors.py --check` in its CI.
5. **A new failure test**: when a fix makes a failure visible, its test makes the call fail and checks the words on screen (`tests/integration/errorPass.test.ts` has the pattern).

## Cache pass

A standing rule (the same pattern as the loop pass). Every piece of kept state that can go stale or grow is listed mechanically and carries its key, invalidation and bound.

1. **Every kept-state row carries a cache comment**, added in the same commit as the cache: `// cache: VERDICT — key=…; invalidated=…; bound=…` on its line or just above. The gate enforces it: `node tools/list_caches.mjs --check` (in `npm run gates`, pre-commit and CI). Kept state is a module-level or class collection written after load, a module/class scalar used as a memo (lazy init, `??=`, a timestamp, a value read from I/O), a closure memo, a `useRef` used as a cache, and a value mirrored from a file at load. Verdicts: **OK**, **FIX-STALE** (can serve stale data the user would notice), **FIX-UNBOUNDED** (can grow without limit: name the growth source), **ADD-CACHE**, **REMOVE** (no gain), **NOT-WORTH**.
2. **Think about invalidation when the board, the controller, the launcher or the update channel changes.** Those are where a cache goes stale here.
3. **Re-run the full pass when a release adds caches, polls or library-scan reads.** `node tools/list_caches.mjs --firmware ../DS5Dongle` lists every row, including `useMemo` / `useCallback`, localStorage keys, clock checks and repeated reads (`repeat-io`, `dup-read`, `poll-io`, `effect-io`). Re-check every verdict and update the tables in `docs/CACHE_PASS_<date>.md`. The owner picks the batches.

## Resource budgets

A standing rule, the game-development way: the app is a little tool for a controller, so it sips resources, and every change fits its budget first. The limits live in one place, [`tools/budgets.json`](tools/budgets.json), and [`docs/BUDGETS.md`](docs/BUDGETS.md) explains each one and the last measurement.

1. **The budgets are a gate.** Idle frames ≤ 10/s on every page (window shown, nothing changing), CPU shown and idle < 2% of a core (main + renderer + utility), CPU hidden in the tray < 0.5% (every process), memory ≤ 275 MB PSS after 10 minutes without the GPU process (reported apart), and memory growth < 5 MB over a 30-minute soak. `tools/check_budgets.sh` measures them on its own hidden copy (own HOME and port 9420, Xvfb 1920x1080, private D-Bus, no USB/hidraw, simulated board with the controller put down, Fake games) and prints a PASS/FAIL table.
2. **When it runs.** `--quick` (~10 min) once per release, in the same step as the UI checker (`docs/TEST_PLAN.md`); `--long` (~55 min, the soak) for a stable release candidate. Not in CI and not in agents' spot checks: it needs a display server and minutes of wall time, and CI runners' timing is too noisy to judge 0.5%.
3. **New visuals state their idle cost**, in the commit and in a comment where they're drawn: frames per second while shown and idle, what stops it while hidden, and what it costs on the CPU fallback. The default is the cheaper option; anything that draws continuously needs the owner's OK and a row in `docs/BUDGETS.md`.
4. **A failing budget is fixed, not raised.** A limit changes only with the owner's OK, in the same commit as the reason in `docs/BUDGETS.md`. The GPU process's CPU is reported, not judged (software rendering on the test display inflates it).
