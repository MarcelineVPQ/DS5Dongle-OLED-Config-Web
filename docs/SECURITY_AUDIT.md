# Security Audit

**Audit date:** 2026-10-10 (desktop app introduction)
**Scope:** the Electron main process, preload, renderer, device access, external links, build and dependency supply chain
**Overall posture:** **GOOD** for the threat model below; one platform gap is recorded and tracked (Linux OS sandbox).

## Threat model

The app runs locally and talks to one USB device. It loads no remote content and has no accounts or secrets. Outbound requests come only from the main process (the renderer has no network access): the signed update feed and its downloads on GitHub, and Sony's controller firmware version list (below). What matters:

1. **Renderer compromise** (e.g. a malicious dependency in the UI bundle) must not reach the OS or other USB devices.
2. **Navigation / window.open** must not load remote content into a privileged window.
3. **Self-update** (Phase 3) must not run a corrupted or unexpected binary.
4. **Supply chain**: dependencies are pinned, audited, and updated deliberately.

## Controls in place

| Control                    | Where                                    | Detail                                                                                                                                                                                 |
| -------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Renderer isolation         | `electron/main/index.ts`                 | `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webSecurity: true`                                                                                                 |
| Minimal preload            | `electron/preload/index.ts`              | Exposes one fixed object (`window.desktop`); no `ipcRenderer`, no Node APIs                                                                                                              |
| Web permissions            | `lockDownSession()`                      | Every permission request denied (so no microphone or camera capture); permission checks pass only for `usb`, `speaker-selection` and `media` with mediaType `audio` (output device names, so the narrator can play on the controller speaker), from the app origin |
| USB device allowlist       | `electron/main/devices.ts`               | WebUSB limited to 054C:0CE6, 054C:0DF2 (dongle) and 2E8A:000F (RP2350 BOOTSEL). Chromium additionally blocks the protected HID/audio classes, so only the vendor interface is reachable |
| Navigation / new windows   | `createWindow()`                         | `will-navigate` blocks every URL but the app's own page (the exact packaged `index.html`, or the dev server's origin), which is also the only page trusted for IPC and WebUSB; `setWindowOpenHandler` always denies and opens only allowlisted https URLs (`electron/main/urls.ts`: github.com, marcelinevpq.github.io, zacksly.itch.io, 42pixelstudios.com, controller.dl.playstation.net for Sony's PlayStation Accessories page) in the system browser           |
| Content Security Policy    | `electron.vite.config.ts`                | `default-src 'self'; script-src 'self'`, no `unsafe-eval`, no remote origins, fonts self-hosted, assets never inlined as `data:`                                                          |
| Single instance            | `requestSingleInstanceLock()`            | Prevents two processes contending for the USB claim                                                                                                                                      |
| Games library | `electron/main/games/{details,running,libraryStore}.ts`, `src/desktop/games/library.ts`, `electron/main/games/artRequest.ts` (`ds5-art://`) | artwork is served by a privileged custom scheme `ds5-art://art/<game key>/<kind>` (CSP `img-src` adds `ds5-art:` only): `artRequestTarget` accepts exactly two path segments, a key matching `GameKeySchema` (scan-shaped, no paths) and a kind from a fixed set, and rejects anything else, including encoded slashes and broken encoding (unit-tested); only files the last scan resolved for that game are returned, and only while Games consent is on (otherwise 404), so the page can't read any other file; the running-game watcher reads `/proc` (user's own processes; only `SteamAppId`/`SteamGameId`/`HEROIC_APP_*` from `environ`); on **Windows** it runs `%SystemRoot%\System32\tasklist.exe /fo csv /nh` (image names only, by full path, no shell) and matches them against the `.exe` names in each scanned game's install folder (read once, three levels, capped); GOG Galaxy games come from `%SystemRoot%\System32\reg.exe query HKLM\SOFTWARE\WOW6432Node\GOG.com\Games /s` and Epic games from the JSON manifests in `%ProgramData%\Epic\EpicGamesLauncher\Data\Manifests` (read-only; game page links are built from validated ids only: `goggalaxy://openGameView/<digits>`, `com.epicgames.launcher://apps/<[\w.-]+>?action=launch&silent=true`); Steam's own categories (game, soundtrack, software, video…) come from `appcache/appinfo.vdf`, read-only by a bounds-checked binary parser that stops at anything unexpected (unit-tested with truncated and foreign files); Steam's install folder comes from `%SystemRoot%\System32\reg.exe query HKCU\Software\Valve\Steam /v SteamPath` (read-only, full path, no shell) or Program Files and polls only while Games consent is on (consent is re-checked when a scan started under consent finishes, and stopping reports "no game running" so a game profile is undone); channels: `desktop:games-details` (read-only: per-game info from the scan, including the install folder path, which the page shows), `desktop:games-running` (read-only: the running game's key or null), `desktop:running-game` (main → page push: the same key on change), `desktop:library-get` / `-set-profile` / `-delete-profile` / `-set-mine` / `-set-restore` / `-set-layout` / `-delete-layout` (the library file; a layout is a strict zod schema: id `[a-z0-9-]{1,40}`, name 1-40 characters, exactly 16 entries each 0-15 or 0xFF, the same rule the firmware enforces); the library file (`userData/game-library.json`) is zod-validated on read (a bad file is set aside) and every IPC write is a strict zod schema (game key, title ≤ 300, profile values in range, no remaps); **game actions** (`desktop:game-action`, `electron/main/games/actions.ts`) take only a scan key and an action name from a fixed list: the main process builds the launcher link itself from the scanned ids (`steam://rungameid|gameproperties|controllerconfig|nav/games/details/<numeric appid>`, `heroic://launch?appName=<encoded>&runner=<fixed>`, `lutris:rungame/<[\w.-]+ slug>`) and opens only folders the scan found (install folder, Proton/Wine prefix) with `shell.openPath`, after checking the path is a directory (launcher configs could name a file, which `openPath` would run); whether a launcher is installed is asked of `xdg-mime` asynchronously (3 s timeout), never blocking the main process; the page never supplies a URL or a path; **art colors** (`desktop:game-art-color`, a scan key only) are computed in the main process from the scanned art file with `nativeImage` (`artColor.ts`) and returned as `#rrggbb`, so the page never reads image pixels |
| Audio tests | `electron/main/audioTest.ts`, `SpeakerTest`/`MicTest` in `src/desktop/live/PartPanel.tsx` | the page still gets no microphone access (the session keeps denying `media`): the mic test (`desktop:mic-test`, no arguments) runs in the main process with PipeWire's `pw-record`/`pw-cat`, only on the source/sink whose name is the DualSense's (`pactl list short`), records 3 s into memory, plays it back on the controller speaker and drops it (never written to disk), Linux only; one test at a time, every child process bounded (SIGTERM, then SIGKILL after 1 s; playback at most clip + 3 s) so a stuck PipeWire tool can't wedge later tests; the level goes to the page on `desktop:mic-level` (main → page push, a number 0..1 only); the speaker test is Web Audio routed with `setSinkId` to the output labelled like the DualSense, never the PC's speakers |
| Updater                    | `electron/main/updater.ts`, `src/update/manifest.ts`, `electron/main/feedSignature.ts` | **signed feed:** `latest.json` must carry an Ed25519 signature (`latest.json.sig`) from a key in `TRUSTED_KEYS` (CI signs with a GitHub Actions secret, `tools/sign_manifest.mjs` in the firmware repo; unsigned, tampered or foreign-signed feeds are refused before parsing, so the app, firmware and Proton downloads all hang off a signed root); zod-validated manifest; downloads only from GitHub release hosts; streamed SHA-256 + exact size, fail closed; strictly-newer versions only; the renderer never touches the network (firmware bytes are verified in main, then handed over); **update channel** (App settings, `updateChannel`): "dev" reads `latest-dev.json` (+ `.sig`) from the same repo with the same keys and checks, never anything else; the only path that installs an older version is `desktop:back-to-stable` and `desktop:dev-channel-preview` (read-only: the newest development build's app and firmware versions and app notes from the dev feed, fetched and signature-checked exactly like an update check, without switching channels; the notes are Markdown shown through the same renderer as the in-app README/CHANGELOG) (no arguments): it switches to the stable feed and offers that feed's version even when older, and nothing else can (`isNewer` everywhere else); downloaded files must still match the manifest's size and hash and the AppImage name pattern |
| Official controller firmware check | `electron/main/officialFirmware.ts`, `src/protocol/officialFirmware.ts` | **check only:** the app never downloads or installs Sony firmware. One outbound host, `fwupdater.dl.playstation.net` (`OFFICIAL_FIRMWARE_HOSTS`), one fixed URL (`/fwupdater/info.json`, the version list Sony's PlayStation Accessories app reads): a plain HTTPS GET with no body, no added headers, `credentials: "omit"`, `redirect: "error"`, a 10 s timeout and a 16 KiB cap (content-length and the bytes read); nothing about the user, the controller or the dongle is sent. The answer is parsed leniently in shape but strictly in value (`FwUpdate<4 hex>LatestVersion` = `0x` + 4 hex digits, any unreadable line rejects the whole answer, ≤ 64 keys) and only numbers reach the page. Runs only with *Check for updates automatically* on, or when the user presses Refresh on the Controller info card (`desktop:official-controller-firmware`, a zod boolean "asked"); cached 24 h in memory (a manual refresh refetches at most once a minute), one request at a time, never at startup. Gated by `tests/security/electron.test.ts` (host allowlist, and only reviewed modules may call `net.fetch`) and `tests/unit/officialFirmware.test.ts` |
| Privileged setup (Windows) | `electron/main/windowsSetup.ts`          | *Repair USB driver* (`desktop:repair-windows-usb`, no arguments): one UAC prompt runs a fixed PowerShell script, passed as `-EncodedCommand` (base64 UTF-16LE, no shell parsing), through PowerShell by its full path under `%SystemRoot%`. It only deletes Windows' cached USB answers for the dongle's own IDs (`usbflags\054C0CE60100`, `054C0DF20100`) and `pnputil /remove-device` for `USB\VID_054C&PID_0CE6*` / `0DF2*` entries (Windows re-creates them on the next plug-in); no input from the page. Gated by `tests/security/electron.test.ts` |
| Privileged setup           | `electron/main/linuxSetup.ts`            | The only root action (Linux udev rule) runs through `pkexec` with a fixed script; paths are positional arguments, never interpolated; the rule file ships in the app's resources and is handed to root through a private temporary copy (root cannot read the AppImage mount) |
| Renderer → main IPC        | `electron/main/ipc.ts`                   | Fixed channel table; every message checks the sender (our window, our page) and parses its payload with zod; tray icons must be size-capped PNG data URLs                              |
| DOM sinks                  | `.hooks/check_dom_sinks.sh` + ESLint      | No `innerHTML`/`eval`/`new Function`; two documented `dangerouslySetInnerHTML` uses render bundled build-time SVGs only                                                                |
| Regression tests           | `tests/security/electron.test.ts`        | Allowlists and the window/session/CSP baseline                                                                                                                                           |
| Dependencies               | `package.json`, Dependabot, `npm-audit.yml` | Exact versions, chosen ≥ 2 weeks after release; weekly grouped Dependabot PRs; CI fails on high-severity advisories in shipped dependencies                                         |
| SAST / secrets             | `security-scans.yml`                     | Semgrep (security-audit, secrets, typescript, react, javascript, owasp-top-ten) and Gitleaks over full history, weekly and on every push                                             |

## Open items

| #   | Severity | Item                                                                                                                                                                                                 | Plan                                                                                                         |
| --- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| O1  | LOW      | **Linux sandbox on Ubuntu 23.10+ needs our AppArmor profile.** Where AppArmor restricts unprivileged user namespaces, electron-builder's AppImage `AppRun` (its probe is `unshare -Ur true`) starts the app with `--no-sandbox`. The one-time Linux setup (*Set up USB access*, pkexec) now also installs `resources/linux/ds5-dongle-configurator.apparmor` to `/etc/apparmor.d/` on such systems: an unconfined profile with `userns`, the same as Ubuntu's own for Chrome, Brave and VS Code, attached to the AppImage's `/tmp/.mount_*/{AppRun,ds5-dongle-configurator}` so the probe and the app both get it. Verified on Ubuntu 26.04: no `--no-sandbox`, the renderer in its own user and PID namespaces with seccomp (mode 2) and NoNewPrivs. Until the user runs the setup (or if they skip it) the app runs as before, without the OS sandbox. ADR-0004 | Ship a .deb with the profile, like VS Code (no setup step) |
| O2  | LOW      | `style-src 'unsafe-inline'` in the CSP (React inline `style` props)                                                                                                                                  | Move remaining inline styles to classes, then drop it                                                        |
| O3  | INFO     | Self-update: the feed is signed (above), so a compromised GitHub account or mirror can't redirect installed apps, but the builds themselves aren't code-signed (Windows SmartScreen warns). Releases carry GitHub build-provenance attestations (`gh attestation verify FILE -R MarcelineVPQ/DS5Dongle-OLED-Edition`). The loopback test feed (`DS5_UPDATE_MANIFEST`, 127.0.0.1 only) works in packaged builds by design, for pre-release testing; a test key (`DS5_UPDATE_PUBKEY`) is only accepted together with it. The signing key's loss means no further updates can be published to installed apps (rotation: ship a new key in `TRUSTED_KEYS` one release ahead) | Windows code signing (e.g. SignPath for open source) |
| O4  | INFO     | Dev-only dependency advisories (e.g. moderate `sprintf-js` via tooling) are reported but not shipped                                                                                                 | Track via Dependabot                                                                                         |
